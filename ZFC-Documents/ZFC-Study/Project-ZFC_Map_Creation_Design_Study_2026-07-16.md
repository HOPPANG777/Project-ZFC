## 1. 이번 학습의 목적

2026-07-13 작업에서는 `Point`, `TileType`, `TileGrid`, `Map`의 기본 책임과 질의 함수를 정리했다.

이번 작업에서는 당시 미결정 사항으로 남겨 둔 다음 문제를 결정했다.

- 빈 `Map`을 허용할 것인가?
- 서로 다른 너비를 가진 행을 허용할 것인가?
- `TILE_NONE`을 맵 내부 지형으로 허용할 것인가?
- 유효하지 않은 절차적 생성 결과를 어떻게 처리할 것인가?
- `MapGenerator`, `MapFactory`, `Map`, 전투 준비 시스템의 책임을 어떻게 나눌 것인가?
- 검증된 그리드를 어떤 타입으로 표현할 것인가?
- 완성된 `Map`의 소유권을 어떤 방식으로 전달할 것인가?
- 생성 성공과 실패를 어떤 결과 계약으로 표현할 것인가?

프로젝트의 학습 원칙도 다시 확인했다.

- 프로젝트 작성자가 직접 코드를 작성한다.
- AI는 완성 코드를 대신 작성하지 않는다.
- 구현 전 책임, 소유권, 불변 조건, 실패 정책을 먼저 정한다.
- 설계 질문과 작은 테스트 사례를 통해 구현 방향을 좁힌다.
- 작성된 코드는 이후 별도로 검토한다.

## 2. 현재 Map 구현의 위치

현재 `Map`은 다음 기능을 가진다.

- `TileGrid` 소유
- 맵 크기 조회
- 좌표가 범위 안인지 검사
- 좌표의 `TileType` 조회
- 지형 자체의 통행 가능 여부 검사

현재 기본 생성자는 `tiles`를 채우지 않으므로 빈 `Map`을 만든다. 그러나 이번 설계를 통해 빈 `Map`을 유효한 런타임 지형으로 인정하지 않기로 했다.

따라서 기존 기본 생성자는 최종 생성 계약과 맞지 않으며, 검증된 지형을 통해서만 `Map`이 생성되도록 구조를 변경한다.

## 3. 빈 Map을 허용하지 않는 이유

`tiles`가 비어 있는 `Map`은 현재 질의 함수만 놓고 보면 안전하게 동작할 수 있다.

```text
GetSize()       -> (0, 0)
Contains(...)   -> false
TileAt(...)     -> TILE_NONE
IsWalkable(...) -> false
```

그러나 안전하게 질의할 수 있다는 사실과 게임에서 유효하다는 사실은 다르다.

```text
메모리 접근상 안전한 상태
!=
게임 규칙상 유효한 상태
```

빈 `Map`은 다음 중 무엇을 뜻하는지 명확하지 않다.

- 아직 생성되지 않은 맵
- 생성에 실패한 맵
- 로딩 중인 맵
- 전투가 종료되어 제거된 맵
- 실수로 초기화하지 않은 맵
- 의도적으로 크기가 0인 맵

이 상태들을 모두 빈 `Map` 하나로 표현하면 렌더러와 전투 시스템이 매번 의미를 추측해야 한다.

이번 설계에서는 다음 문장을 계약으로 정했다.

```text
Map이 존재한다는 것은 구조적으로 유효한 지형이 완성됐다는 뜻이다.
아직 맵이 없는 상태는 Map 내부가 아니라 상위 시스템이 표현한다.
```

## 4. 행과 열이 모두 필요한 이유

`TileGrid`는 바깥 `vector`가 행을, 각 행의 안쪽 `vector`가 열을 표현한다.

따라서 다음 두 상태는 모두 유효한 맵이 아니다.

- 바깥 `vector`에 행이 하나도 없음
- 행은 있지만 해당 행에 타일이 하나도 없음

한 행과 여러 열로 이루어진 일직선 맵이나 여러 행과 한 열로 이루어진 일직선 맵은 구조적으로 유효하다. 너비와 높이가 모두 0보다 크기 때문이다.

다만 실제 전투를 진행하기에 충분한지는 구조 검증이 아니라 전투 준비 검증에서 판단한다.

## 5. 서로 다른 행 너비를 거부하는 이유

2차원 `vector`는 각 행의 길이를 자동으로 같게 만들지 않는다. 다음처럼 행마다 다른 개수의 타일을 저장할 수 있다.

```text
행 0: #####  -> 너비 5
행 1: #..    -> 너비 3
행 2: ####   -> 너비 4
```

이 구조는 C++ 컨테이너로서는 표현 가능하지만 Project-ZFC의 사각 격자 맵으로서는 유효하지 않다.

행 너비가 다르면 다음 문제가 생긴다.

- 맵 전체의 너비를 하나로 정의할 수 없다.
- 첫 행을 기준으로 계산한 `GetSize()`와 실제 데이터가 달라진다.
- 렌더러가 일정한 `x` 범위를 순회할 수 없다.
- 같은 좌표가 행에 따라 존재하거나 존재하지 않을 수 있다.
- 이동, 공격 범위, 경로 탐색이 매번 행 길이를 따로 처리해야 한다.
- 비정형 모양인지 생성기 버그인지 구분하기 어렵다.

따라서 모든 행은 첫 행과 같은 너비를 가져야 한다.

## 6. 비정형 맵과 직사각형 저장 구조

화면에서 방 모양이 불규칙하게 보이더라도 저장하는 타일 그리드는 직사각형으로 유지할 수 있다.

```text
전체 직사각형을 TILE_WALL로 채운다.
-> 방과 통로 부분만 TILE_FLOOR로 파낸다.
```

예를 들어 실제 이동 공간이 불규칙해도 모든 행의 너비는 같다.

```text
###########
####...####
####...####
##.......##
##.......##
###########
```

이번 단계에서는 사용하지 않는 공간을 `TILE_WALL`로 표현한다.

향후 벽과도 다른, 화면에 그리지 않는 맵 바깥 공간이 필요하다면 의미가 분명한 별도 지형 타입을 검토할 수 있다. 그 경우에도 그리드 자체는 직사각형으로 유지한다.

## 7. TILE_NONE의 최종 의미

현재 `TILE_NONE`은 실제 플레이 지형이 아니다.

```text
TILE_NONE
-> 해당 좌표에 유효한 지형이 없음
-> 범위 밖 조회 또는 초기화되지 않은 상태를 나타냄
```

맵 내부에서 사용하지 않는 공간을 표현하기 위해 `TILE_NONE`을 사용하면 다음 두 상태를 구분할 수 없게 된다.

- 맵 범위 밖
- 맵 안에 있지만 비어 있는 공간

따라서 `TileLayout` 내부에는 `TILE_NONE`이 하나라도 존재할 수 없다.

절차적 생성기는 전체 그리드를 먼저 `TILE_WALL`로 채우고 필요한 위치를 `TILE_FLOOR`로 변경한다. 이 과정이 지켜졌는데 `TILE_NONE`이 남았다면 생성 구현의 초기화 누락을 의심해야 한다.

## 8. 확정한 Map 구조 불변 조건

완성된 `Map`은 다음 조건을 항상 만족해야 한다.

1. 행이 하나 이상 존재한다.
2. 열이 하나 이상 존재한다.
3. 모든 행의 너비가 같다.
4. 내부에 `TILE_NONE`이 없다.
5. 너비와 높이를 프로젝트 좌표 타입으로 표현할 수 있다.
6. 외부에서 행을 추가하거나 제거할 수 없다.
7. 외부에서 개별 지형을 임의로 변경할 수 없다.

다음 조건은 `Map`의 구조 불변 조건이 아니다.

- FLOOR가 반드시 존재해야 함
- 플레이어 스폰 위치가 있어야 함
- 적을 배치할 수 있어야 함
- 모든 FLOOR가 연결돼 있어야 함
- 출구까지 이동할 수 있어야 함

예를 들어 모든 칸이 `TILE_WALL`인 직사각형은 구조적으로는 올바르다. 전투에 사용할 수 있는지는 별도 시스템에서 판단한다.

## 9. 구조 유효성과 전투 가능성 분리

검증은 세 수준으로 나눈다.

### 9.1 MapFactory의 구조 검증

- 행과 열 존재 여부
- 직사각형 여부
- 내부 `TILE_NONE` 여부
- 크기 표현 가능 여부
- 지원하는 지형 값 여부

### 9.2 MapGenerator의 생성 품질 검증

- 방과 통로가 생성 규칙을 만족하는가?
- 바닥 공간이 존재하는가?
- 필요한 연결성이 확보됐는가?
- 일반적인 스폰 후보 공간이 존재하는가?
- 이번 절차적 생성 후보를 사용할 것인가?

### 9.3 CombatSetup의 특정 전투 검증

- 이번 전투의 플레이어와 적을 배치할 수 있는가?
- 플레이어와 적 사이의 최소 거리를 만족하는가?
- 보스가 차지할 공간이 있는가?
- 유닛 배치가 겹치지 않는가?
- 특정 적 조합이 이동하고 공격할 수 있는가?

이렇게 분리하면 `MapGenerator`가 `EnemyDefinition`이나 전투 규칙을 알 필요가 없다.

## 10. 예상 가능한 생성 실패와 구조적 오류

절차적 생성 과정의 실패는 모두 같은 성격이 아니다.

### 예상 가능한 후보 탈락

알고리즘이 정상적으로 동작해도 무작위 결과에 따라 발생할 수 있다.

- 방 연결 실패
- 스폰 공간 부족
- 출구 도달 불가
- 최소 방 크기 미달
- 전투 공간 부족

처리 방향:

```text
이번 후보 폐기
-> 다른 시드로 재생성
```

### 구조적 계약 위반

전체 그리드를 고정 크기의 WALL로 초기화하는 규칙이 지켜졌다면 일반적인 무작위 실패로 보기 어렵다.

- 행이 없음
- 열이 없음
- 행마다 너비가 다름
- 내부에 `TILE_NONE`이 남음

처리 방향:

```text
버그 또는 설정 오류로 기록
-> 무한 재시도 방지
-> 안전한 대체 맵 또는 로딩 실패 정책 사용
```

## 11. 재생성과 로딩 정책

유저에게 절차적 생성 후보 탈락을 매번 오류 창이나 프로그램 종료로 보여주지 않는다.

상위 로딩 흐름이 다음을 담당한다.

```text
맵 생성 시도
-> 후보 품질 검증
-> 구조 검증
-> 전투 배치 검증
-> 실패 원인에 따라 재시도
-> 최대 횟수 초과 시 대체 맵
```

재시도 횟수에는 반드시 한도를 둔다. 성공할 때까지 무한 반복하면 불가능한 생성 설정에서 로딩이 끝나지 않을 수 있다.

유저와 개발자에게 보여주는 정보도 구분한다.

```text
유저
-> 로딩 화면 또는 안전한 대체 맵

개발자
-> 실패 상태, 시드, 시도 횟수, 진단 로그
```

실패한 시드를 기록하면 같은 후보를 다시 생성해 문제를 재현할 수 있다.

## 12. 생성자는 결과를 반환할 수 없음

C++ 생성자에는 반환 타입이 없다. 따라서 `Map` 생성자가 성공 또는 실패 열거형을 반환하는 구조는 사용할 수 없다.

생성 성공과 실패를 알리는 책임은 `MapGenerator`, `MapFactory`, 또는 이들이 반환하는 결과 타입이 가져야 한다.

최종 흐름은 다음처럼 정했다.

```text
MapGenerator가 후보 TileGrid 생성
-> MapFactory가 구조 검증
-> 검증 성공 시 TileLayout 생성
-> TileLayout으로 Map 생성
-> 생성 결과 반환
```

## 13. explicit에서 학습한 내용

`explicit`은 생성자를 통한 암시적 형 변환을 막는 C++ 키워드다.

`TileGrid`와 `Map`은 의미가 다르다.

```text
TileGrid
-> 아직 검증되지 않았을 수 있는 원시 지형 데이터

Map
-> 불변 조건 검증을 통과한 완성된 지형 객체
```

따라서 컴파일러가 `TileGrid`를 자동으로 `Map`으로 바꾸게 두기보다 개발자가 생성 의도를 명확히 표현하도록 제한하는 편이 안전하다.

`explicit`은 다음 기능을 제공하지 않는다.

- 데이터 검증
- 메모리 이동
- 접근 제어
- 복사 방지

런타임 비용 없이 컴파일 단계의 허용 문법을 제한한다.

이번 설계에서는 생성 접근 자체를 `MapFactory` 경로로 제한하므로 직접 생성자의 암시적 변환 문제도 함께 줄어든다.

## 14. stdexcept에서 학습한 내용

`stdexcept`는 표준 예외 타입을 제공하는 표준 라이브러리 헤더다.

대표적인 표준 예외 타입:

- 잘못된 인수를 나타내는 예외
- 범위를 벗어난 접근을 나타내는 예외
- 실행 중 오류를 나타내는 예외
- 논리 계약 위반을 나타내는 예외

`throw` 자체는 C++ 언어 기능이며 `stdexcept`가 제공하는 것은 아니다.

이번 설계에서는 예상 가능한 구조 검증 실패를 생성 결과 상태로 전달한다. 예외는 검증 결과를 대신하는 유일한 수단으로 사용하지 않는다.

예외가 발생했다고 반드시 게임이 종료되는 것은 아니다. 상위 계층에서 처리하면 로그, 대체 맵, 안전한 로딩 실패 등으로 전환할 수 있다.

## 15. utility와 std::move에서 학습한 내용

`utility`는 `std::move`, `std::forward`, `std::pair`, `std::swap` 같은 범용 도구를 제공한다.

`std::move` 자체가 데이터를 물리적으로 옮기지는 않는다. 원본 자원을 다른 객체가 가져가도 된다는 의도를 표현한다. 실제 이동은 대상 타입의 이동 생성자 또는 이동 대입 연산자가 처리한다.

```text
복사
-> 원본 유지
-> 새 저장 공간에 내용을 복제

이동
-> 원본의 자원을 새 객체가 이어받음
-> 불필요한 전체 복사를 줄일 수 있음
```

이동된 객체는 파괴하거나 새 값을 대입할 수 있는 유효한 상태로 남지만, 기존 내용이 유지된다고 가정해서는 안 된다.

## 16. 참조 전달과 소유권 이전의 차이

참조는 일반적으로 기존 객체를 빌려서 사용하는 방식이다. 참조로 전달받았다는 사실만으로 소유권이 이전되지는 않는다.

읽기 전용 참조로 받은 `TileGrid`를 `Map`이 계속 소유하려면 다음 중 하나가 필요하다.

- 내부 데이터로 복사
- 원본보다 짧게 참조하고 원본 소유자가 수명을 보장

이번 설계는 완성된 후보 데이터를 이후에 다시 사용하지 않으므로 이동을 통한 소유권 전달을 선택했다.

```text
MapGenerator의 TileGrid
-> TileLayout으로 이동
-> Map이 TileLayout 소유
```

## 17. 값 소유와 스마트 포인터

스마트 포인터는 `Map` 객체 자체를 누가 소유하고 언제 파괴할지 결정한다. `TileGrid`를 생성자에 어떻게 전달할지와는 별개의 문제다.

### 값 소유

객체를 멤버로 가진 상위 객체가 수명을 소유한다. 상위 객체가 파괴되면 `Map`과 내부 자원도 자동으로 정리된다.

### unique_ptr

하나의 소유자가 `Map`의 삭제 책임을 가진다. 이동하면 삭제 책임도 새 `unique_ptr`로 이전된다.

### shared_ptr

여러 소유자가 같은 객체의 수명에 참여한다. 마지막 소유자가 사라질 때 객체가 파괴된다.

여러 시스템이 같은 `Map`을 읽는다는 이유만으로 공동 소유가 필요한 것은 아니다.

```text
여러 곳에서 접근
!=
여러 곳에서 공동 소유
```

## 18. Map의 최종 소유권 정책

완성된 `Map`은 `unique_ptr`로 단독 소유하기로 했다.

```text
MapFactory
-> 생성 직후 unique_ptr<Map> 소유

CombatState
-> unique_ptr를 이동받아 최종 소유

CombatSystem / Renderer / CombatSetup
-> Map을 읽기 전용으로 참조
```

전투 상태가 파괴되거나 맵을 교체하면 `unique_ptr`가 `Map`, `TileLayout`, 내부 타일 자원을 자동으로 정리한다.

현재 `shared_ptr`를 사용하지 않는 이유:

- 맵 수명의 최종 책임자가 명확함
- 렌더러가 맵 수명을 결정할 필요가 없음
- 공동 소유가 필요한 요구사항이 없음
- 순환 소유 가능성을 피할 수 있음

## 19. 복사 생성자와 기본 생성자의 차이

복사 생성자는 기본 생성자를 대신하지 않는다.

```text
기본 생성
-> 기존 Map 없이 객체 생성

복사 생성
-> 이미 존재하는 Map으로 새 Map 생성
```

빈 `Map`을 허용하지 않으므로 테스트나 디버그를 이유로 기본 생성자를 남기지 않는다. 테스트에서도 실제 생성 계약대로 작은 유효 그리드를 사용한다.

맵 데이터가 커질 것을 고려해 이동을 선택했으므로, 맵 전체 복사는 현재 목적과 맞지 않는다. 지금은 `Map`과 `TileLayout`을 복사하지 않고 이동과 단독 소유를 중심으로 설계한다. 향후 스냅숏이나 명시적 복제가 필요해지면 별도의 복제 정책을 검토한다.

## 20. TileLayout 이름을 선택한 이유

검증 완료 타입의 초기 후보는 `ValidatedTileGrid`였다. 의미는 정확하지만 타입이 무엇인지보다 어떤 과정을 거쳤는지를 이름에 담아 길었다.

검증을 통과해야만 존재할 수 있는 타입은 이름에 `Validated`를 반복할 필요가 없다. 유효성은 생성 제한과 불변 조건으로 보장한다.

최종 이름은 `TileLayout`으로 결정했다.

```text
TileGrid
-> 생성 중인 가변 타일 데이터

TileLayout
-> 검증이 끝난 불변 타일 배치

Map
-> TileLayout을 소유하고 지형 질의를 제공하는 객체
```

`TileLayout`은 단순한 타입 별칭이 아니라 자체 책임과 접근 제한을 가진 타입이어야 한다.

## 21. MapFactory를 도입하는 이유

처음에는 `MapGenerator`만 `Map`을 생성할 수 있게 제한하는 방안을 검토했다. 그러나 향후 맵 데이터의 출처는 늘어날 수 있다.

- 절차적 생성기
- 고정 튜토리얼 맵
- 저장 파일 로더
- 맵 에디터
- 네트워크 데이터
- 실패 시 대체 맵

따라서 특정 호출자 하나만 허용하기보다 어떤 호출자도 검증을 우회할 수 없게 만드는 것이 더 확장성이 좋다.

```text
중요한 것은 누가 생성 요청을 했는지가 아니다.
어떤 경로에서도 검증되지 않은 Map을 얻을 수 없어야 한다.
```

`MapFactory`는 다음을 담당한다.

- 후보 `TileGrid`의 구조 검증
- 검증 성공 시 `TileLayout` 생성
- `TileLayout`으로 `Map` 생성
- 성공 또는 실패 결과 생성
- 부분적으로 생성된 객체를 외부에 노출하지 않음

## 22. MapFactory와 별도 Validator

현재 구조 검증을 사용하는 공식 경로는 `MapFactory` 하나이므로 별도 `MapValidator` 클래스는 당장 필수가 아니다.

다음 상황이 생기면 분리를 검토한다.

- 에디터가 상세 검증 결과를 직접 표시함
- 저장 파일 로더가 같은 검증을 재사용함
- 여러 팩토리가 공통 검증을 사용함
- 검증 규칙이 커지고 독립 테스트가 필요함

초기에는 `MapFactory` 안에서 생성 처리와 검증 논리를 개념적으로 구분하되, 실제 재사용 요구가 생길 때 별도 컴포넌트로 추출한다.

## 23. MapCreationResult의 계약

`unique_ptr<Map>`만 반환하면 실패 이유를 알 수 없다. 상태 열거형만 반환하면 성공한 `Map`의 소유권을 전달할 수 없다.

따라서 생성 결과는 다음 두 정보를 함께 표현한다.

- 생성 상태
- 성공한 `Map`의 단독 소유권

성공 결과의 계약:

```text
상태: 성공
Map: 반드시 존재
Map 상태: 모든 구조 불변 조건 만족
```

실패 결과의 계약:

```text
상태: 구체적인 실패 이유
Map: 반드시 없음
부분 생성 객체: 외부에 노출하지 않음
```

허용하지 않는 상태:

- 성공인데 `Map`이 없음
- 실패인데 `Map`이 존재함

결과는 `unique_ptr`를 포함하므로 복사하지 않고 이동으로 전달한다.

## 24. MapGenerationResult와 MapCreationResult 구분

두 결과는 실패 의미가 다르다.

### MapGenerationResult

`MapGenerator`가 반환한다.

```text
성공
-> 후보 TileGrid 존재

실패
-> 연결 실패, 공간 부족 등 예상 가능한 후보 탈락
```

### MapCreationResult

`MapFactory`가 반환한다.

```text
성공
-> unique_ptr<Map> 존재

실패
-> 빈 크기, 행 너비 불일치, TILE_NONE 등 구조 계약 위반
```

이 둘을 분리하면 재시도와 버그 기록 정책을 구분할 수 있다.

## 25. 그래픽 API 이식성과 책임 분리

저수준 그래픽 API로 옮길 때 최소한의 수정만 하려면 핵심 맵 타입이 그래픽 시스템을 몰라야 한다.

```text
Map / MapFactory / TileLayout
-> Windows 콘솔 타입을 모름
-> 텍스처와 스프라이트를 모름
-> 그래픽 API 타입을 모름

ConsoleRenderer
-> 현재 문자로 지형 출력

향후 GraphicsRenderer
-> TileType에 대응하는 스프라이트 출력
```

벽 스프라이트 로딩 실패는 `Map` 구조 실패가 아니라 그래픽 자원 실패다. 다음 단계의 검증은 서로 섞지 않는다.

- 그래픽 자원 검증
- 맵 구조 검증
- 맵 생성 품질 검증
- 전투 배치 검증

상위 로딩 시스템이 각 단계를 조정한다.

## 26. 최종 의존성 구조

```text
TileType
   |
TileGrid
   |
MapGenerator --------> MapGenerationResult
   |
후보 TileGrid
   |
MapFactory ----------> MapCreationResult
   |                         |
TileLayout                  unique_ptr<Map>
   |                         |
Map <------------------------
   |
CombatSetup
   |
CombatState가 최종 소유
   |
CombatSystem / Renderer가 읽기 전용 참조
```

상위 로딩 흐름은 생성, 검증, 재시도, 대체 맵 선택, 전투 준비를 조정한다.

## 27. 이번에 확정한 최종 문장

```text
TileGrid는 만들어 가는 데이터다.
TileLayout은 구조 검증이 끝난 불변 타일 배치다.
Map은 TileLayout을 소유하고 지형 질문에 답한다.
MapFactory는 검증되지 않은 데이터가 Map이 되는 것을 막는다.
MapGenerator는 절차적 후보의 생성 품질을 책임진다.
CombatSetup은 특정 전투의 배치 가능성을 책임진다.
CombatState는 unique_ptr로 Map을 단독 소유한다.
Renderer는 Map을 소유하지 않고 읽기만 한다.
```

## 28. 구현 단계에서 지킬 원칙

- 검증 실패 데이터를 자동 수정하지 않는다.
- 짧은 행을 WALL로 자동 채우지 않는다.
- 긴 행을 자동으로 자르지 않는다.
- 내부 `TILE_NONE`을 자동으로 WALL로 바꾸지 않는다.
- 성공과 실패가 동시에 표현되는 결과를 허용하지 않는다.
- 부분적으로 생성된 `Map`을 외부에 노출하지 않는다.
- 재시도는 상위 로딩 흐름에서 제한 횟수만 수행한다.
- 대체 맵도 동일한 `MapFactory` 검증 경로를 통과시킨다.
- 테스트와 디버그에서도 빈 `Map`을 특별 허용하지 않는다.
- 그래픽 표현 요구를 `Map`의 지형 계약에 섞지 않는다.
