# Project-ZFC 맵 시스템 설계 학습 정리

작성일: 2026-07-13  
대상: Project-ZFC 콘솔 프로토타입의 `Point`, `Map`, `TileType`

## 1. 프로젝트와 학습 방식

Project-ZFC는 단순히 게임을 완성하는 것뿐 아니라, 직접 설계하고 구현하면서 개발 실력을 높이기 위한 프로젝트다.

따라서 개발 과정에서는 다음 원칙을 사용한다.

- 코드는 프로젝트 작성자가 직접 작성한다.
- AI는 정답 코드를 먼저 제공하기보다 문제를 나누고 생각할 질문을 제시한다.
- 구현 전에는 클래스의 책임, 데이터의 소유자, 유효한 상태를 먼저 결정한다.
- 작성한 코드는 결과만 보지 않고 왜 동작하는지, 어떤 입력에서 실패하는지 검토한다.
- 기능을 추가하기 전에 작은 테스트 사례로 현재 단계가 정확한지 확인한다.

## 2. 오늘 확정한 전체 구조

맵과 관련된 책임은 다음처럼 분리한다.

```text
MapGenerator
    └─ 절차적으로 TileGrid를 생성한다.

Map
    └─ 완성된 지형 데이터를 소유하고 조회 기능을 제공한다.

CombatSystem 또는 MovementSystem
    ├─ Map의 지형 통행 가능 여부를 확인한다.
    ├─ 유닛의 위치와 점유 여부를 확인한다.
    └─ 모든 규칙을 만족할 때 이동을 수행한다.

ConsoleRenderer
    ├─ Map의 지형을 읽는다.
    ├─ 플레이어와 적의 위치를 읽는다.
    ├─ 공격 예고 정보를 읽는다.
    └─ 출력 우선순위에 따라 CMD 문자를 그린다.
```

핵심 의존성 방향은 다음과 같다.

```text
Map ─────────────┐
                 ├─> CombatSystem
Unit States ─────┘

Map ─────────────┐
Unit States ─────┼─> ConsoleRenderer
Telegraphs ──────┘
```

`Map`과 `Unit`은 서로를 직접 참조하지 않는다. 둘을 함께 알아야 하는 상위 시스템이 양쪽 데이터를 조합한다.

## 3. Map의 책임과 책임이 아닌 것

### Map이 소유할 것

- 맵의 지형 데이터
- 좌표가 맵 범위 안인지 판단하는 기능
- 특정 좌표의 `TileType`을 반환하는 기능
- 특정 지형이 통행 가능한지 판단하는 기능

### Map이 소유하지 않을 것

- 플레이어와 적의 위치
- 유닛의 생존 상태
- 공격 예고와 위험 타일
- CMD 출력 문자
- 전투 턴 상태
- 이동 행동 전체의 성공 여부

`Map::IsWalkable()`은 지형만 판단한다. 바닥 위에 적이 있어도 지형 자체는 걸을 수 있다. 실제 이동 가능 여부는 상위 전투 시스템이 지형과 유닛 점유를 함께 보고 판단해야 한다.

## 4. 타일 정보를 레이어로 구분한 이유

한 좌표에는 여러 정보가 동시에 존재할 수 있다.

```text
지형: Floor
점유: Player
효과: Danger
```

이것을 단일 `TileType`으로 표현하면 플레이어가 이동했을 때 원래 지형을 잃거나, 플레이어와 위험 예고가 동시에 존재하는 상태를 표현하기 어렵다.

따라서 현재 `TileType`은 지형만 표현한다.

```text
TILE_NONE  → 유효한 지형이 없음
TILE_WALL  → 벽
TILE_FLOOR → 바닥
```

플레이어, 적, 공격 예고는 별도 전투 데이터로 관리하고 렌더링할 때만 합성한다.

## 5. Point 타입 설계

Windows의 `POINT`를 핵심 전투 코드에 사용하지 않고 프로젝트 자체 타입을 사용하기로 했다.

```text
ZFC::Point
├─ int x
└─ int y
```

이유는 다음과 같다.

- Core가 Windows API에 의존하지 않게 한다.
- 맵 좌표라는 프로젝트 도메인의 의미를 표현한다.
- 이후 다른 렌더링 API나 자체 엔진으로 옮기기 쉽다.
- Windows 콘솔 좌표가 필요하면 렌더러 경계에서 `COORD` 등으로 변환할 수 있다.

`Point`는 단순 값 타입이므로 `x`, `y`를 public으로 두어도 된다. 반면 유닛이 소유한 위치 상태는 외부에서 임의로 수정할 수 없도록 별도의 행동 인터페이스로 보호해야 한다.

### int와 size_t의 역할 차이

```text
int Point
→ 좌표와 이동 계산
→ (-1, 0) 같은 범위 밖 목적지를 표현할 수 있음

std::size_t
→ vector의 원소 개수와 인덱스
→ 음수를 표현하지 않음
```

플레이어가 `(0, 0)`에서 왼쪽으로 이동하려 하면 목적지는 `(-1, 0)`이다. `Point`가 `size_t`라면 `-1`이 거대한 양수로 언더플로되므로 좌표에는 signed 타입이 필요하다.

vector에 접근할 때는 다음 경계를 지킨다.

```text
음수 좌표 검사
→ 맵 범위 검사
→ 안전한 경우에만 size_t로 변환하여 vector와 비교하거나 접근
```

## 6. 2차원 vector 구조

가독성을 우선하여 다음 구조를 선택했다.

```cpp
using TileRow = std::vector<TileType>;
using TileGrid = std::vector<TileRow>;
```

접근 순서는 항상 다음과 같다.

```cpp
tiles[y][x]
```

의미는 다음과 같다.

```text
바깥 vector
→ 행들의 목록
→ tiles.size()는 높이

안쪽 vector
→ 한 행의 열 목록
→ tiles.front().size()는 너비
```

예시:

```text
tiles =
[
    [A, B, C],
    [D, E, F]
]

높이: tiles.size()          = 2
너비: tiles.front().size()  = 3

tiles[0][0] = A
tiles[0][2] = C
tiles[1][0] = D
tiles[1][2] = F
```

`size()`는 원소를 다시 세는 함수가 아니라 이미 저장된 크기를 반환하므로 `O(1)`이다.

## 7. size 멤버를 제거한 이유

`size`와 `tiles`를 동시에 저장하면 동일한 정보를 두 곳에서 관리하게 된다.

```text
size       = 10 × 6
실제 tiles = 8 × 6
```

둘이 달라지면 어느 값이 실제 맵 크기인지 알 수 없다. 중복 상태를 계속 동기화하는 것은 유지보수 비용과 버그 가능성을 늘린다.

현재 구조에서는 `tiles`를 단일 진실 공급원으로 사용한다.

```text
height = tiles.size()
width  = tiles가 비어 있지 않다면 tiles.front().size()
```

## 8. Map이 보장해야 할 불변 조건

완성된 `Map`은 다음 조건을 지키는 것이 좋다.

1. 모든 행의 길이가 같다.
2. 너비와 높이는 프로젝트에서 사용하는 정수 범위 안이다.
3. 빈 맵을 허용할지 정책이 정해져 있다.
4. 완성된 맵 내부에서 `TILE_NONE`을 실제 지형으로 사용하지 않는다.
5. 외부에서 `TileGrid`의 행을 제거하거나 길이를 바꿀 수 없게 한다.

행 길이가 다른 데이터의 예:

```text
[
    [Floor, Floor, Wall],
    [Floor],
    [Wall, Floor]
]
```

이 구조에서는 하나의 너비를 정의할 수 없다. `Map` 생성 시 직사각형 여부를 한 번 검증하면 이후의 조회 함수는 매번 검사하지 않아도 된다.

## 9. 현재 Map 질의 함수의 계약

### GetSize

```text
목적: 맵의 너비와 높이를 반환한다.
반환: Point
Point.x = 열 개수
Point.y = 행 개수
```

빈 그리드에서는 `front()`를 호출할 수 없으므로 먼저 `tiles.empty()`를 확인한다.

`Point`는 aggregate 구조체이므로 별도 생성자 없이 중괄호로 반환할 수 있다.

```cpp
return ZFC::Point{ x, y };
```

반환 타입이 이미 알려져 있으면 다음 표현도 가능하다.

```cpp
return { x, y };
```

이는 operator가 아니라 aggregate 초기화다.

### Contains

```text
목적: 좌표가 실제 TileGrid 범위 안인지 검사한다.
반환: 범위 안이면 true, 아니면 false
```

판정 순서:

```text
1. x 또는 y가 음수인지 확인한다.
2. y가 바깥 vector의 행 범위 안인지 확인한다.
3. x가 해당 행의 열 범위 안인지 확인한다.
4. 모든 조건을 만족할 때만 true를 반환한다.
5. 나머지 모든 실행 경로에서 false를 반환한다.
```

`&&`는 왼쪽 조건이 거짓이면 오른쪽을 실행하지 않는다. 따라서 반드시 행 범위 검사를 왼쪽에 두고, 안전한 경우에만 `tiles[position.y]`에 접근한다.

C++에서는 다음과 같은 수학식 형태의 연속 비교를 사용할 수 없다.

```cpp
0 <= x < width // 잘못된 의미
```

이는 다음처럼 해석된다.

```text
(0 <= x)의 bool 결과를 다시 width와 비교
```

두 조건을 `&&`로 분리해야 한다.

### TileAt

```text
목적: 특정 좌표의 TileType을 반환한다.
접근: tiles[position.y][position.x]
```

현재 선택한 정책:

```text
유효한 좌표 → 해당 TileType
범위 밖     → TILE_NONE
```

이 정책을 사용할 경우 `TILE_NONE`은 실제 플레이 지형이 아니라 “유효한 타일이 없음”을 나타내야 한다.

다른 가능한 정책으로는 `assert`, 예외, `std::optional<TileType>`이 있다. 프로젝트가 성장하면 호출 실수를 조용히 숨기지 않는 정책이 더 적합한지 다시 검토한다.

### IsWalkable

```text
목적: 해당 좌표의 지형 자체가 통행 가능한지 판단한다.
```

현재 규칙:

```text
TILE_FLOOR → true
TILE_WALL  → false
TILE_NONE  → false
범위 밖    → TileAt이 NONE을 반환하므로 false
```

“NONE이 아닌가?”를 검사하면 WALL까지 통행 가능해지므로, 현재 허용하는 타입인 FLOOR를 명시적으로 검사한다.

```text
허용되지 않은 타입을 제외하는 방식보다
허용된 타입을 명시하는 방식이 새 타입 추가에 안전하다.
```

## 10. const에 관해 확인한 내용

맵을 읽기만 하는 멤버 함수는 함수 뒤에 `const`를 붙인다.

```text
GetSize() const
Contains(...) const
TileAt(...) const
IsWalkable(...) const
```

이렇게 하면:

- `const Map`에서도 호출할 수 있다.
- 함수 내부에서 실수로 맵 상태를 변경하는 것을 막는다.
- 함수가 조회 기능이라는 의도를 표현한다.

반면 다음 매개변수의 앞쪽 `const`는 값으로 전달된 복사본에만 적용된다.

```cpp
const ZFC::Point position
```

`Point`는 정수 두 개를 가진 작은 값 타입이므로 다음처럼 값으로 전달해도 충분하다.

```cpp
ZFC::Point position
```

## 11. 오늘 발견한 주요 C++ 실수

### 비 void 함수의 반환 누락

다음 구조에서는 조건이 거짓일 때 아무 값도 반환하지 않는다.

```text
if (condition)
    return value;

함수 종료
```

`bool`, `TileType` 등 비 `void` 함수는 가능한 모든 실행 경로에서 값을 반환해야 한다. 반환이 누락되면 정의되지 않은 동작이 발생한다.

### size와 인덱스의 혼동

행이 2개라면:

```text
tiles.size() = 2
유효 인덱스  = 0, 1
tiles[2]     = 범위 밖
```

`size()`는 마지막 인덱스가 아니라 원소 개수다.

### 좌표 순서의 혼동

좌표 표현은 `(x, y)`지만 2차원 vector 접근은 행을 먼저 선택하므로 다음 순서를 사용한다.

```cpp
tiles[y][x]
```

### 조건문의 마지막 반환값 실수

`IsWalkable()`에서 FLOOR일 때 `true`를 반환한 뒤 마지막에도 `true`를 반환하면 모든 타일이 통행 가능해진다. 각 입력별 예상 결과를 표로 작성하면 이런 실수를 찾기 쉽다.

## 12. 절차적 생성 방향

최종적으로 절차적 생성은 `MapGenerator`가 담당한다.

권장 흐름:

```text
1. 전체 TileGrid를 WALL로 채운다.
2. 방과 통로를 FLOOR로 파낸다.
3. 모든 행이 같은 길이인지 확인한다.
4. 필요한 경우 연결성과 스폰 가능 위치를 검증한다.
5. 완성된 TileGrid로 Map을 만든다.
```

WALL에서 시작해 FLOOR를 파내면 미생성 공간이 자동으로 막혀 있고, 외부로 열린 구멍이 우연히 생길 가능성이 낮다.

`MapGenerator`가 실제로 등장하기 전에는 타입 별칭을 맵 영역에 두고, 두 번째 사용처가 생겼을 때 적절한 공용 파일로 옮기는 방식도 가능하다.

## 13. CMD 렌더링 방향

렌더러는 Map의 지형 데이터를 변경하지 않고 여러 레이어를 화면에서만 합성한다.

출력 우선순위 예시:

```text
1. 플레이어가 있으면 @
2. 적이 있으면 E
3. 공격 예고가 있으면 !
4. WALL이면 #
5. FLOOR이면 ·
```

렌더러는 `GetSize()`로 좌표 순회 범위를 확인하고 `TileAt()`으로 각 지형을 읽을 수 있다. 전체 `TileGrid`를 복사해서 반환하는 `GetTile()`은 필요하지 않다.

## 14. 현재 함수 검증 사례

크기 `3 × 2`인 직사각형 맵을 기준으로 다음 결과를 확인한다.

```text
Contains({ 0,  0}) → true
Contains({ 2,  1}) → true
Contains({ 3,  1}) → false
Contains({ 2,  2}) → false
Contains({-1,  0}) → false
Contains({ 0, -1}) → false
```

타일 판정:

```text
TileAt(Floor 좌표) → TILE_FLOOR
TileAt(Wall 좌표)  → TILE_WALL
TileAt(범위 밖)    → TILE_NONE
```

통행 판정:

```text
IsWalkable(Floor 좌표) → true
IsWalkable(Wall 좌표)  → false
IsWalkable(범위 밖)    → false
```

## 16. 다음 구현 순서

1. 현재 `GetSize`, `Contains`, `TileAt`, `IsWalkable`을 작은 예제로 실행한다.
2. FLOOR와 WALL이 섞인 `3 × 2` 테스트 그리드를 준비한다.
3. 정상 좌표와 경계 밖 좌표를 모두 테스트한다.
4. Map의 생성 계약과 빈 맵 정책을 결정한다.
5. 직사각형 불변 조건을 Map이 어떻게 보장할지 설계한다.
6. 단순한 `MapGenerator`를 만들어 전체 WALL에서 내부 FLOOR를 생성한다.
7. 지형만 CMD에 출력한다.
8. 이후 플레이어와 적을 Map 밖의 데이터로 추가하고 렌더러에서 합성한다.

## 17. 오늘의 핵심 문장

```text
Map은 지형을 소유하고 질문에 답한다.
Unit은 자신의 상태를 소유한다.
CombatSystem은 여러 상태를 조합해 행동을 검증한다.
Renderer는 상태를 변경하지 않고 화면에서만 합성한다.
```

그리고 구현에서는 다음을 기억한다.

```text
tiles[y][x]
size()는 개수이고 마지막 인덱스가 아니다.
모든 비 void 함수는 모든 경로에서 값을 반환해야 한다.
좌표는 음수가 필요할 수 있지만 컨테이너 크기는 음수가 없다.
중복 상태를 저장하지 않으면 동기화할 코드도 필요 없다.
```
