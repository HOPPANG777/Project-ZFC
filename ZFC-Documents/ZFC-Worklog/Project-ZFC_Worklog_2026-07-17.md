- `TileLayout.h/.cpp`를 작성하고 프로젝트에 등록했다.

## 4. 세부 작업 내용

### 4.1 맵 생성 체크리스트 위치 정리

맵 생성 구현 체크리스트는 설계 학습 자료가 아니라 실제 구현 순서와 완료 조건을 관리하는 문서다. 문서의 역할에 맞게 `ZFC-Study`에서 `ZFC-Plan`으로 이동했다.

현재 기준 문서:

- [맵 생성 구현 체크리스트](../ZFC-Plan/Project-ZFC_Map_Creation_Implementation_Checklist_2026-07-16.md)
- [TileLayout 구현 계획](../ZFC-Plan/Project-ZFC_TileLayout_Plan_2026-07-16.md)

### 4.2 TileGrid 분리

기존에는 `TileRow`와 `TileGrid` 별칭이 `Map.h`에 있어 다른 타입이 원시 타일 데이터를 사용하려면 `Map` 정의까지 알아야 했다.

이를 다음 책임으로 분리했다.

| 타입 | 책임 |
| --- | --- |
| `TileRow` | 한 행을 이루는 타일 목록 |
| `TileGrid` | 여러 행으로 이루어진 검증 전 원시 타일 데이터 |
| `Map` | 완성된 지형을 소유하고 지형 질문에 답하는 타입 |

`TileGrid`는 다음 상태도 표현할 수 있다.

- 행이 없는 상태
- 열이 없는 상태
- 행마다 너비가 다른 상태
- 내부에 `TILE_NONE`이 남아 있는 상태

따라서 `TileGrid`의 존재만으로는 유효한 맵이라고 판단하지 않는다.

### 4.3 맵 타입 네임스페이스 정리

`TileType`을 `ZFC` 네임스페이스로 이동하고 관련 사용처를 갱신했다. `Map.h`의 불필요한 시스템 include를 정리하고, 타입 설명과 파일 이력을 코딩 컨벤션에 맞게 보강했다.

이번 작업을 통해 확인한 기준:

- 프로젝트 도메인 타입은 전역 이름 충돌을 피할 수 있게 관리한다.
- 헤더는 실제로 필요한 의존성만 포함한다.
- 타입을 이동할 때 선언뿐 아니라 반환 타입과 모든 사용처도 함께 확인한다.
- 주석은 코드 번역보다 책임과 제약을 설명해야 한다.

### 4.4 TileLayout 책임 확정

`TileLayout`은 단순한 `TileGrid` 별칭이 아니라 구조 검증을 통과한 상태를 표현하는 별도 타입으로 결정했다.

```text
TileGrid
-> 검증되지 않은 원시 타일 데이터

TileLayout
-> 구조 검증을 통과한 불변 타일 배치
```

`TileLayout` 객체가 존재한다는 사실 자체가 구조 검증 성공의 증거가 되어야 한다. 따라서 별도의 `검증됨` 상태 플래그는 저장하지 않는다.

### 4.5 TileLayout 생성 제한

생성 제한은 다음 세 단계로 나누어 생각했다.

| 단계 | 목적 |
| --- | --- |
| 생성 경로 제한 | 외부에서 빈 객체나 원시 데이터로 직접 생성하지 못하게 함 |
| 생성 권한 지정 | `MapFactory`만 검증 완료 데이터를 이용해 생성하게 함 |
| 생성 후 수정 차단 | 검증된 불변 조건이 외부 변경으로 깨지지 않게 함 |

적용한 정책:

- 기본 생성 금지
- 외부 원시 `TileGrid` 직접 생성 금지
- `MapFactory`에만 비공개 생성 접근 권한 부여
- 복사 생성과 복사 대입 금지
- 이동 생성과 이동 대입 허용
- 불필요한 사용자 정의 소멸 로직 미작성
- 전체 `TileGrid` Getter 미제공
- 행과 개별 타일 Setter 미제공

### 4.6 전방 선언과 friendship 학습

`MapFactory`는 아직 구현되지 않았지만 `TileLayout`이 `MapFactory` 객체를 소유하거나 함수를 호출하지 않으므로 전체 정의가 필요하지 않았다.

현재 `TileLayout`에는 다음 관계만 필요하다.

```text
TileLayout
-> MapFactory라는 타입의 이름을 앎
-> MapFactory에 비공개 생성 접근 권한을 부여함
```

실제 `MapFactory` 정의와 검증 로직은 이후 단계에서 추가한다. 전방 선언은 정의를 대신하는 기능이 아니라, 현재 파일에서 전체 정의가 필요하지 않음을 표현하는 기능이다.

### 4.7 TileLayout 소유권 정책

스마트 포인터와 값 타입 이동을 구분했다.

| 이동 단계 | 이동되는 대상 | 새 소유자 |
| --- | --- | --- |
| 1 | `TileGrid` 내부 자원 | `TileLayout` |
| 2 | `TileLayout` | `Map` |
| 3 | `unique_ptr<Map>` | `MapCreationResult` |
| 4 | `unique_ptr<Map>` | 최종 `CombatState` |

`TileLayout` 자체는 `unique_ptr`로 소유하지 않는다. 이후 `Map`의 값 멤버로 소유할 예정이다.

현재는 맵 복제 요구가 없고 전체 2차원 컨테이너의 의도하지 않은 복사를 막기 위해 복사를 금지했다. 스냅숏이나 런타임 지형 변경 요구가 실제로 생기면 일반 복사, 명시적 복제, 변경분 저장 중 적합한 정책을 다시 검토한다.

### 4.8 TileLayout 질의 함수

`TileLayout`은 내부 저장 구조 전체를 노출하지 않고 `Map`에 필요한 최소 읽기 기능만 제공한다.

| 질의 | 계약 |
| --- | --- |
| 크기 조회 | 열 개수와 행 개수를 반환 |
| 범위 검사 | 음수와 컨테이너 범위 밖 좌표를 거부 |
| 타일 조회 | 유효 좌표는 실제 타일, 범위 밖은 `TILE_NONE` 반환 |

통행 가능 여부는 `TileLayout`의 책임에 포함하지 않았다. 타일 배치는 특정 좌표에 어떤 지형이 있는지만 답하고, 해당 지형을 걸을 수 있는지는 `Map`의 게임 규칙으로 남긴다.

### 4.9 선언과 구현 분리

`TileLayout.h`에는 다음 내용만 남겼다.

- 타입의 책임과 Synopsis
- `MapFactory` 전방 선언과 접근 권한
- 생성, 복사, 이동 정책
- 읽기 전용 질의 함수 선언
- 비공개 `TileGrid` 멤버

함수 본문은 `TileLayout.cpp`로 이동하고 `Map.cpp`와 동일한 구분선 및 함수 정의 헤더 형식을 적용했다.

### 4.10 Visual Studio 프로젝트 구조 정리

새 `TileLayout.cpp`와 `TileLayout.h`를 프로젝트에 등록했다. 이후 솔루션 탐색기에서 파일 책임을 빠르게 구분할 수 있도록 다음 필터를 구성했다.

- `Map/Map`
- `Map/TileLayout`
- `Map/Tile`
- `Core/Point`
- `Core/Vector`

## 5. 오늘 학습한 핵심 개념

### 5.1 클래스라는 사실만으로 유효성이 보장되지는 않는다

별도 클래스를 만드는 것만으로 잘못된 상태가 사라지지는 않는다. 유효한 타입을 만들려면 생성 경로 제한, 검증 권한 집중, 생성 후 수정 차단이 함께 필요하다.

### 5.2 타입 자체를 검증의 증거로 사용할 수 있다

`TileLayout`에 검증 상태를 저장하고 매번 확인하는 대신, 검증을 통과한 경우에만 객체가 존재할 수 있게 만든다.

```text
TileLayout 존재
-> 구조 검증 성공
```

### 5.3 구조 검증과 생성 품질 검증은 다르다

| 검사 | 담당 |
| --- | --- |
| 행·열 존재, 직사각형, `TILE_NONE`, 크기 범위 | `MapFactory` |
| FLOOR 존재, 방과 통로, 연결성, 일반 스폰 후보 | `MapGenerator` |
| 특정 플레이어·적 배치, 최소 거리, 보스 공간 | `CombatSetup` |

모든 칸이 벽인 직사각형은 구조적으로 유효하지만 절차적 전투 맵 후보로는 부적합할 수 있다.

### 5.4 Setter보다 생성 시점의 완전한 초기화가 안전하다

빈 객체를 만든 뒤 Setter로 데이터를 넣으면 Setter 호출 전이나 호출 누락 시 잘못된 객체가 존재한다. 검증 완료 데이터를 제한된 생성 경로에서 한 번에 인계받으면 부분 초기화 상태를 만들지 않을 수 있다.

### 5.5 복사와 이동은 서로 다른 정책이다

복사는 동일한 전체 데이터를 하나 더 만들고, 이동은 기존 자원의 소유자를 변경한다. 현재 맵 데이터는 복제 요구가 없으므로 복사를 금지하고 `Map`으로 전달하기 위한 이동만 허용했다.

### 5.6 확장성은 미래 기능을 모두 미리 추가하는 것이 아니다

현재 사용처가 하나뿐인 `MapValidator`를 미리 만들지 않기로 했다. 대신 `MapFactory` 내부에서 검증과 생성을 개념적으로 분리해, 실제 두 번째 검증 사용처가 생기면 검증 로직만 추출할 수 있게 한다.

### 6.3 빌드 중 해결한 문제

처음 새 `TileLayout` 파일을 빌드했을 때 한국어 주석이 현재 코드 페이지에서 표현되지 않는다는 `C4819` 경고가 발생했다. 프로젝트는 경고를 오류로 처리하므로 빌드가 중단됐다.

두 파일을 기존 프로젝트와 같은 UTF-8 BOM 형식으로 정규화한 뒤 Debug와 Release 빌드가 모두 성공했다.

또한 C++ 프로젝트는 `dotnet build`에서 Visual C++ 대상 파일을 찾지 못했으므로 Visual Studio의 MSBuild를 사용해 검증했다.

### 7.2 MapFactory 이후 확인할 TileLayout 불변 조건

- 높이가 0보다 큼
- 너비가 0보다 큼
- 모든 행의 너비가 같음
- 내부에 `TILE_NONE`이 없음
- 너비와 높이를 `int` 범위로 표현 가능
- 지원하지 않는 타일 값이 없음

현재 `TileLayout`은 이 조건을 직접 검사하지 않는다. 이후 `MapFactory`가 검증을 통과한 데이터만 비공개 생성 경로에 전달해야 한다.

## 8. 현재 남아 있는 설계 사항

### 8.1 이동 대입과 불변성의 의미

현재 이동 대입을 허용하므로 기존 `TileLayout` 전체를 다른 유효한 배치로 교체할 수 있다.

- 불변을 행과 개별 타일을 임의로 수정할 수 없다는 의미로 정의하면 현재 정책을 유지할 수 있다.
- 생성 후 전체 배치 교체까지 금지한다면 이동 생성만 허용하고 이동 대입은 다시 검토해야 한다.

### 8.2 Map의 현재 소유 구조

현재 `Map`은 아직 `TileGrid`를 직접 소유한다. `TileLayout` 구현 완료만으로 최종 생성 파이프라인이 완성된 것은 아니다.

향후 다음 구조로 변경해야 한다.

```text
현재
Map -> TileGrid

목표
Map -> TileLayout -> TileGrid
```

### 8.3 런타임 테스트 미실시

`MapFactory`가 아직 존재하지 않아 정상 생성 경로를 이용한 런타임 질의 테스트는 수행하지 않았다. 현재 검증 결과는 접근 정책에 대한 정적 검토와 컴파일·링크 검증이다.

## 9. 다음 작업

체크리스트 순서에 따라 다음 작업을 진행한다.

1. `MapCreationStatus` 열거형의 상태와 실패 의미 결정
2. 열거형 명명 규칙과 첫 값 계약 적용
3. `MapCreationResult`의 성공·실패 불변 조건 설계
4. 기존 `Map`이 `TileGrid` 대신 `TileLayout`을 소유하도록 변경
5. `MapFactory` 구조 검증 순서 구현
6. 정상 `3 x 2` 생성 테스트
7. 빈 크기, 행 너비 불일치, 내부 `TILE_NONE` 실패 테스트
8. `unique_ptr<Map>` 소유권 이동 테스트
9. Debug x64와 Release x64 재검증

## 10. 오늘의 핵심 문장

```text
TileGrid는 검증되지 않은 원시 타일 데이터다.
TileLayout은 구조 검증을 통과한 불변 타일 배치다.
MapFactory는 검증되지 않은 데이터가 TileLayout이 되는 것을 막는다.
Map은 TileLayout을 소유하고 지형 질문에 답한다.
검증 성공 여부는 상태 플래그가 아니라 TileLayout 타입 자체로 표현한다.
```
